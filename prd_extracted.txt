1. Executive Summary
This PRD defines a Financial Fraud Detection System that a student can build in four weeks. The system loads a financial transaction dataset, validates and explores it, trains and compares supervised machine learning models, scores transactions with a fraud probability and risk category, and presents the findings in an interactive Streamlit dashboard. Users can also upload a compatible CSV file and receive predictions.
The mentor supplied three distinct datasets, a set of reference notebooks and five Power BI dashboard archives. This PRD treats the three datasets as separate sources with different schemas, target columns, label definitions and fraud prevalence. The notebooks and dashboards are used as references for methods and visual design; they are not assumed to run, or to be complete, without modification.
Key decisions in this PRD
Primary dataset [Recommendation]:
 synthetic_fraud_dataset1.csv (50,000 rows, 14 columns, target Fraud_Label), subject to a Week 1 audit gate. It offers the richest mix of numerical, categorical and temporal fields at a size that trains quickly on a laptop. Its roughly 32% fraud rate is unrealistically high and its data is synthetic, so results must not be presented as evidence of real-world effectiveness.
Optional secondary experiment [Recommendation]:
 credit_card_fraud_dataset.csv (100,000 rows, ~1% fraud) to show how the same pipeline behaves under realistic class imbalance.
Models:
 Logistic Regression (baseline), Decision Tree and Random Forest (comparison), with XGBoost (or another boosting model) and Isolation Forest as optional extras.
Evaluation:
 stratified held-out test set that keeps the original class distribution; resampling only inside training folds; threshold selected on validation data, never on the test set; metrics include precision, recall, F1, ROC-AUC, PR-AUC, confusion matrix and false-positive/false-negative counts.
Interface:
 a five-page Streamlit dashboard (Executive Overview, Transaction Analytics, Fraud Detection, Model Performance, Detailed Transaction Review) with SQLite for lightweight persistence.
Out of scope for v1:
 Kafka, Spark Streaming, e-mail alerts, real-time banking integration, adaptive retraining and deep learning. Real-time processing will not be claimed.
Positioning.
 This is a prototype for educational purposes. It estimates the likelihood that a transaction resembles fraud in the training data. It does not confirm fraud and must not be used to block, freeze or report real customers.
2. Problem Statement
Financial fraud causes direct monetary loss and erodes customer trust. Fraudulent transactions are normally a very small share of all transactions, so they are easy to overlook in manual review and hard for naive models to learn. Two kinds of error carry real cost:
False negatives (missed fraud):
 a fraudulent transaction is treated as legitimate, so the loss is realised.
False positives (false alarms):
 a legitimate transaction is flagged, causing customer friction and analyst workload.
Analysts therefore need (a) a model that ranks transactions by risk, (b) a way to choose how aggressively to flag, and (c) a clear view of where and when suspicious activity concentrates. The mentor's stated objective is to 
build a Machine Learning and Data Analytics system to identify suspicious transactions, analyse fraud patterns and present actionable insights through an interactive dashboard.
A further problem for a learner is methodological: it is easy to produce misleadingly high scores through accuracy on imbalanced data, resampling before the train/test split, or features that leak the label. This PRD builds guardrails against those mistakes into the requirements.

6.3 Recommendation
Primary dataset [Recommendation]: Dataset C (synthetic_fraud_dataset1.csv).
 Reasons:
It is large enough for stable train/validation/test splits and quick enough to train several models on a student laptop.
It contains numerical, categorical and temporal variables, which allows every EDA chart and every dashboard page in this PRD to be built from real columns.
It supports the feature ideas in FR-04 (time-of-day features, balance-based features, daily transaction count) without inventing customer histories.
Dataset A is too sparse in features to show meaningful modelling or analytics; Dataset B is small, and its suspicious-keyword field is a likely leakage source.
Accepted weaknesses.
 Dataset C's 32% fraud rate is not realistic and is likely generated by a simple rule or random process. Consequently:
PR-AUC must be interpreted relative to the prevalence (a random model's PR-AUC equals the positive-class rate, about 0.32 here), not relative to 0.5.
Any strong performance must be explained cautiously: it may reflect the synthetic generating rule rather than learnable real-world fraud signal.
The final report must state that performance on this dataset does not establish effectiveness on real banking transactions.
Optional secondary experiment [Recommendation]: Dataset A.
 Re-running the same pipeline on Dataset A demonstrates behaviour at ≈1% prevalence, where a "predict everything legitimate" model is already ≈99% accurate. Use only the columns that exist (no invented features). Report its results in a separate table, never pooled with Dataset C.
Dataset B [Recommendation]:
 retain for reference only. Use it as an experiment only if the intern can demonstrate (a) the suspicious-keyword field is not label-derived, or (b) results are reported with and without that field.

9. ML Methodology and Evaluation Strategy
9.1 Data splitting
Hold-out test set:
 20% of rows, stratified on the target, locked away until final evaluation.
Validation:
 use stratified 5-fold cross-validation on the remaining 80% (or a 60/20/20 split) for model selection, hyper-parameter tuning, and threshold selection.
Temporal check:
 the datasets are described as synthetic, so a random stratified split is acceptable. If a date field exists, also run one time-ordered split (train on earlier dates, test on later ones) as a robustness check and report it separately. This is a recommendation, not a requirement, because transactions in a real system are time-dependent.
Seed:
 one project-level RANDOM_STATE in the configuration file.
9.2 Preprocessing pipeline
Numeric: median imputation → scaling (needed for Logistic Regression; harmless for trees).
Categorical: most-frequent imputation → one-hot encoding with handle_unknown="ignore"; for any high-cardinality field consider frequency encoding or exclusion.
Date-derived features computed by a custom transformer (hour, weekday, month).
Everything is assembled in a single scikit-learn Pipeline so that fit sees training data only and the same fitted object is used at inference.

Fast; discards data; compare against class weights
SMOTE
Training folds only, after encoding of categories
Needs numeric features; can create unrealistic synthetic samples; use via imblearn pipeline
Threshold tuning
Validation predictions
Often as impactful as resampling; applies to every model
Never resample before splitting. Never evaluate on resampled data. Report the unresampled test distribution next to every metric table.
9.5 Why accuracy is not enough
At roughly 1% fraud (Dataset A), a model that labels every transaction as legitimate reaches about 99% accuracy while detecting no fraud. Even at about 32% fraud (Dataset C), accuracy hides how many frauds are missed and how many legitimate customers are flagged. Therefore recall, precision, F1, PR-AUC and the confusion matrix are mandatory, and the accuracy of the majority-class baseline must be reported alongside.

9.7 Threshold selection
Obtain out-of-fold (or validation) probabilities for the chosen model.
State a business rationale before looking at results (for example: "catch at least X% of fraud while keeping the flag volume manageable"; X is chosen by the team and documented).
Compute precision, recall and flag counts for thresholds from 0.05 to 0.95; plot them.
Pick the threshold that satisfies the rule; save it with the model.
Apply the threshold once to the untouched test set and report results.
9.8 Hyper-parameter tuning and model selection
Keep tuning modest: a small grid or randomised search with stratified cross-validation, scored by PR-AUC (or recall at a minimum precision).
Select the final model on validation results and parsimony (a simpler model is preferred when scores are similar).
Report variability (e.g., mean ± standard deviation across folds) so that small differences are not over-interpreted.
9.9 Leakage prevention summary
Split before any fitted transformation.
Fit imputers, encoders and scalers on training data only (via the pipeline).
Resample inside training folds only.
Exclude identifiers and any label-derived or post-event fields.
Do not tune the threshold or hyper-parameters on the test set.
Run the single-feature screen from Section 6.4 and investigate unusually strong features.
9.10 Interpreting results honestly
Because the data is synthetic or of unknown origin, any strong results may reflect the data-generating rule and may not transfer to real transactions. Feature importance describes what the model used, not why fraud happens. Predictions are probabilistic estimates and should never be presented as confirmed fraud.

11.2 Data flow

Evaluate:

 the fitted pipeline, threshold, feature list, metrics and version string are saved.

 the dashboard loads the saved pipeline, validates uploaded data against the schema, predicts, assigns risk categories.
Display:
 results and analytics are rendered; users filter, review and export.
